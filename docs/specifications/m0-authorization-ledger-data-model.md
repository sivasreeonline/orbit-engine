# M0 Authorization Ledger Data Model and Transaction Design

**Status:** Implementation design proposal; no migration is approved or deployed.  
**Authority boundary:** Neon stores the application-side authorization ledger and an auditable mirror of externally authenticated host-incarnation facts. Neon does not become the provider fencing authority and cannot mint host epochs.  
**Execution boundary:** This document does not authorize privileged implementation, Phase A, Phase B, student execution, or production execution.

## 1. Storage ownership

| Data | Authoritative owner | Orbit Engine representation |
|---|---|---|
| Stable host enrollment identity | Independently selected enrollment authority | Immutable host identity reference |
| Provider predecessor inventory and fence outcome | Cloud provider / external fencing authority | Verified evidence reference and signed response digest |
| Host incarnation epoch issuance | External host-incarnation authority | Authenticated issuance receipt mirror |
| Guest durable epoch acceptance | Exact host instance | Independently verified acceptance evidence |
| Phase A authorization decision | Independent security-review process | Immutable signed manifest in R2 plus ledger projection |
| Authorization lifecycle state and run budget | Neon PostgreSQL ledger | Transactional state and append-only event history |
| Evidence bytes and signed manifests | Private immutable R2 bucket | Exact object key, version ID, SHA-256, size and retention metadata |
| Signer trust policy | Independently governed key authority | Pinned key ID/version, algorithm and validity/revocation metadata |

Neon is authoritative for the application-side Phase A ledger only. It is not authoritative for provider state, actual VM isolation, the external host epoch, or cryptographic key revocation unless the external authority supplies authenticated evidence.

## 2. Relational model

All identifiers are UUIDs generated by trusted services. Digests are lowercase SHA-256 hex strings over canonical bytes. Timestamps are UTC timestamptz; trusted-time provenance is recorded separately. Host and authorization identities are never reused.

### 2.1 host_enrollments

One row per stable enrolled host identity.

Required fields: id UUID primary key; external_authority_id; authority_key_version; provider_account_ref; provider_region; provider_resource_ref (opaque references, never credentials); status ENROLLED/QUARANTINED/RETIRED; last_observed_epoch bigint; last_authority_record_version bigint; created_at; updated_at; retired_at.

Constraints:
- Unique external authority + stable host identity.
- Epoch and authority record version never decrease.
- Retired identities cannot be reactivated; replacement enrollment receives a new identity.
- Provider credentials, private keys and bearer tokens are forbidden.

### 2.2 host_epoch_receipts

Append-only mirror of external authority issuance; this table is not an epoch allocator.

Required fields: id; host_enrollment_id; epoch; provider_instance_ref; operation_id; nonce_digest; request_digest; predecessor_set_digest; fence_evidence_ref/digest; authority_id; key_id/version; algorithm; signed_response_ref/digest; signature_bytes_ref; issued_at; authority_record_version; verified_at; verification_report_ref/digest; response_id.

Constraints:
- Unique (host_enrollment_id, epoch), (host_enrollment_id, operation_id), (host_enrollment_id, nonce_digest), and (authority_id, response_id).
- No update/delete of signed receipt facts; corrections are new linked records.
- A receipt is verified only after cryptographic verification against pinned trust metadata and independently resolved evidence. A reference string alone is not verification.

### 2.3 host_epoch_acceptances

Append-only proof that one exact provider instance durably accepted one receipt.

Required fields: id; host_epoch_receipt_id; provider_instance_ref; accepted_epoch; accepted_response_digest; durable_record_digest; readback_evidence_ref/digest; accepted_at; verified_at; verification_report_ref/digest.

Constraints:
- Unique host_epoch_receipt_id; one receipt can be accepted only once.
- Unique provider_instance_ref for an accepted current incarnation.
- Receipt epoch, response digest and provider instance must match exactly.
- This row does not itself prove admission is safe; host readiness still verifies current authoritative status and local controls.

### 2.4 phase_a_authorizations

Mutable current-state projection. Every mutation appends an event in the same database transaction.

Required fields: id UUID primary key; authorization_digest; host_enrollment_id; host_epoch_receipt_id; host_epoch_acceptance_id; security_review_record_ref/digest; fence_001_evidence_ref/digest; host_qualification_ref/digest; manifest_object_key/version_id/sha256/size_bytes; signer_id; signer_key_version; signature_algorithm; signature_object_ref/sha256; state PREPARED/ISSUED/ACCEPTED/CONSUMED/REVOKED/EXPIRED/QUARANTINED; state_version bigint; max_total_runs; consumed_runs; not_before; expires_at; trusted_time_source/evidence_ref; issued_at; accepted_at; revoked_at; expired_at; created_at; updated_at.

Constraints:
- Unique authorization digest and immutable manifest object version.
- ISSUED or later states require exact host, epoch receipt and acceptance bindings.
- max_total_runs > 0 and 0 <= consumed_runs <= max_total_runs.
- expires_at > not_before; terminal states require corresponding terminal event.
- State changes occur only through reviewed procedures; direct application UPDATE is denied.
- REVOKED, EXPIRED and QUARANTINED are terminal.
- Authorization is ineligible when enrollment, receipt, acceptance, key status, review, qualification or evidence is revoked, stale, mismatched or uncertain.

### 2.5 authorization_events

Append-only event ledger for every state transition and administrative/security action.

Required fields: id; authorization_id; sequence_no; prior_state; new_state; prior_state_version; new_state_version; event_type; actor_principal_ref; actor_role; reason_code; request_id; request_digest; evidence_ref/digest; occurred_at; trusted_time_source; previous_event_digest; event_digest.

Constraints:
- Unique (authorization_id, sequence_no) and (authorization_id, request_id).
- Application roles cannot UPDATE or DELETE event rows.
- Event digest chaining detects edits but is not a substitute for an externally anchored signature or immutable backup.
- Retain events and tombstones for the full anti-replay, audit and legal retention period.

### 2.6 authorization_run_claims

One immutable row per unique attempt to consume authorization run budget.

Required fields: id; authorization_id; run_id; request_digest; claim_sequence; claimed_state_version; claim_status CLAIMED/COMPLETED/FAILED/QUARANTINED; claimed_at; finished_at; run_evidence_ref/digest.

Constraints:
- Unique (authorization_id, run_id) and (authorization_id, claim_sequence).
- Same run ID + same request digest returns original claim; changed digest conflicts.
- Claim rows are never deleted and consumed budget is never silently refunded.
- FAILED and QUARANTINED claims remain consumed; no counter decrement is allowed.

### 2.7 authorization_signing_keys

Trust metadata only; private key bytes never enter Neon.

Required fields: authority_id; key_id; key_version; algorithm; public_key_fingerprint; valid_from; valid_until; revoked_at; revocation_reason; trust_bundle_ref/digest; last_verified_at.

Constraints:
- Unique (authority_id, key_id, key_version).
- Revocation is terminal for signing/acceptance. Old public keys may remain for historical signature verification under explicit policy.
- Unknown algorithm, key version, trust bundle or revocation state fails closed.

## 3. Transaction protocols

Every transaction uses bounded statement/transaction timeouts and a stable request ID. The API role receives EXECUTE permission on reviewed procedures only; it cannot update lifecycle projections or append events directly.

### 3.1 Issue authorization

1. Resolve and verify immutable signed manifest, exact R2 object version, SHA-256, signature, signer key version, trusted time and evidence references outside the transaction.
2. Confirm the external host receipt and exact-instance durable acceptance evidence have already been independently verified.
3. Begin a serializable transaction; lock the authorization row (or insert under a unique digest); check expected state version and PREPARED.
4. Re-check database-visible key/revocation projection, host enrollment, epoch receipt, acceptance, review/qualification digests, FENCE-001 pass and expiry window.
5. Insert ISSUED event and update projection with state version +1 in the same transaction.
6. Commit. Resolve lost acknowledgements by request ID and digest; never issue a second authorization.

External signature and R2 readback cannot be atomic with PostgreSQL. Their immutable references and exact digests are verified before the transaction and rechecked during later consumption. Ambiguous outcomes are quarantined.

### 3.2 Accept authorization

Verify target host identity, current accepted epoch, exact authorization digest and manifest version. Require durable host-side acceptance and independent readback. In one serializable transaction, lock the authorization row, compare expected state version, check ISSUED, then re-check expiry, revocation, host/epoch, key and review status. Append ACCEPTED event and update state/version atomically. Any mismatch or unknown commit result denies admission and quarantines pending reconciliation.

### 3.3 Consume a run

A single transaction must:
1. Lock the phase_a_authorizations row with SELECT FOR UPDATE.
2. Check exact authorization digest, ACCEPTED state, host/epoch acceptance, current key/revocation status, trusted time, review/qualification evidence and run policy.
3. Look up (authorization_id, run_id). Same digest returns original claim; changed digest conflicts.
4. Require consumed_runs < max_total_runs.
5. Insert immutable run claim with next sequence.
6. Increment consumed_runs and state_version, and append CONSUMED event in the same transaction.
7. Commit before any calibration process starts.

Concurrent claimers serialize on the authorization row. At most one can claim the final slot. A retry after lost acknowledgement resolves by unique run ID. A crash after commit never refunds the slot; recovery reconciles that run ID and either resumes only the same run within its original deadline or quarantines it.

### 3.4 Revoke authorization

Verify revocation actor/authority and signed reason/evidence. Lock authorization row and compare expected state version. Append REVOKED event and terminal tombstone; set state REVOKED and increment state version. Commit before host/provider side effects. Trigger separately governed host-admission disable and provider fencing; record operation IDs and independently verify outcomes. A crash after ledger commit leaves revocation effective. No run claim may be created or resumed after revocation commits.

A PostgreSQL revocation does not itself kill a running VM. Provider fencing and host admission disable require independent evidence.

## 4. Crash, retry and rollback handling

| Failure boundary | Required behavior |
|---|---|
| Before transaction | No state change; retry same request ID |
| During transaction before commit | Rollback; no state change |
| Commit succeeds, acknowledgement lost | Resolve by request ID, digest and event sequence; never repeat as a new operation |
| R2 upload succeeds, DB insert fails | Quarantine unreferenced immutable object for reconciliation; never overwrite |
| DB row exists, R2 object missing/version differs | QUARANTINED; no acceptance or run claim |
| Signature/key lookup unavailable | Deny; do not trust cached unsigned status |
| Key revoked while acceptance/claim races | Serialize against trusted revocation projection; ambiguous freshness fails closed |
| Two claims race for final slot | Exactly one succeeds |
| Revocation races run claim | Database serialization establishes order; claims after committed revocation fail |
| Neon restore omits newer revocation/event | External anti-rollback checkpoint detects stale ledger; quarantine affected authorizations |
| R2 version deleted or retention weakened | Evidence integrity failure; quarantine and stop qualification |
| Trusted clock unavailable/uncertain | No issue, accept, expiry transition or run claim |

Neon point-in-time restore is not sufficient anti-rollback protection. Before reopening authorization operations after restore, compare restored ledger's latest externally anchored checkpoint/event digest and monotonic sequence with a separately controlled witness. If the witness is unavailable or disagrees, keep the ledger read-only and affected authorizations quarantined.

## 5. Database controls

- Use PostgreSQL row locks and serializable transactions for transitions and run claims; retry serialization failures only with the same request ID/digest.
- Unique constraints are the final concurrency guard, not application-only prechecks.
- Revoke direct UPDATE/DELETE on event and claim tables from application roles.
- Separate migration owner, ledger procedure owner, API role, audit-reader role and break-glass role.
- Audit break-glass access; prohibit routine application use of owner/superuser roles.
- Never log signatures, credentials, private keys, full evidence payloads or student source code in ledger events.
- A host epoch is scoped to enrolled host identity, not a browser user or tenant-provided string.
- Retain event/claim tombstones through maximum replay/rollback horizon; archival preserves unique-key conflict behavior.
- Back up ledger and immutable R2 evidence independently; test restore plus anti-rollback witness reconciliation.

## 6. Evidence and independent verification

For every ISSUED, ACCEPTED, CONSUMED, REVOKED, EXPIRED or QUARANTINED transition, preserve exact manifest bytes/object version/size/SHA-256; signature and signer/key/trust-bundle identity; external host epoch receipt and predecessor-set/provider-fence evidence; exact-instance durable acceptance/readback; security-review record with FENCE-001 pass; host qualification and independent verifier report; request/event digest and state versions; run claim and evidence disposition.

The evidence acquirer, independent verifier, host owner and security reviewer are distinct principals. The verifier retrieves and verifies the exact R2 version and signature independently; database references alone are insufficient.

## 7. Approval gates before migration or implementation

Do not create or apply a production migration until:
1. External authority protocol and provider fencing contract are selected and independently reviewed.
2. Signer algorithms, canonical payload format, key custody, rotation and revocation are approved.
3. R2 create-only/versioning/retention/lock semantics are demonstrated in the target account.
4. Neon role separation, serializable transaction behavior, anti-rollback witness and restore procedure are tested.
5. A threat-reviewed schema/procedure set passes deterministic concurrent-claim, revocation-race, crash-after-commit, restore/rollback and tamper tests.
6. Independent reviewers approve exact migration, procedures, evidence model and operational runbooks.

This is a data and transaction design proposal. It does not prove external/runtime properties and does not authorize execution.


## Cryptographic payload schema references

The typed signed-envelope payload families and their structural validator are defined in the cryptographic trust contract:
- `docs/schemas/m0-host-epoch-response-payload.schema.json`
- `docs/schemas/m0-provider-fence-attestation-payload.schema.json`
- `docs/schemas/m0-phase-a-authorization-payload.schema.json`
- `docs/schemas/m0-key-revocation-payload.schema.json`
- `scripts/validate_m0_crypto_contract.py`

These schemas bind exact identities, epochs, immutable evidence references/digests, the 33-control independent review including `FENCE-001`, and explicit denial of Phase B/student/production execution in the Phase A payload. They validate shape and declared cross-field rules only; they do not authenticate a signature, independently verify provider fencing, or prove external evidence.


### Authorization scope and principal separation clarification

The message payload named `phase-a-authorization` is restricted to `M0_CLEANUP_CALIBRATION_ONLY`; it is not a general host-qualification, full-M0-proof, Phase B, student, or production grant. Its payload explicitly binds five distinct principals: host owner, evidence acquirer, fence verifier, independent security reviewer, and authorization signer. The structural validator rejects role collisions. This supplements, and does not replace, the role/evidence checks in the independent security-review record and cleanup-calibration authorization contract.


### Key lifecycle and trust-bundle transition contract

The append-only key lifecycle event schema is `docs/schemas/m0-crypto-key-lifecycle-event.schema.json`. It defines explicit generation, pending, activation, deprecation, revocation and destruction transitions. Revocation is terminal for signing and admission; a revoked key may never return to ACTIVE. Historical public-key verification is a separate, policy-bounded audit capability and does not restore signing authority.

Trust-bundle successors must increment generation by exactly one, bind the exact previous bundle digest, and preserve authority, root identity and environment. Revocation statements must identify an exact key ID/version and agree with that key's REVOKED status and revocation metadata. Duplicate key-version identities and duplicate revocation identities are rejected by semantic validation.

The ledger remains an application-side projection. An externally anchored anti-rollback checkpoint is required to detect Neon restore to an earlier event/revocation generation. A schema-valid event or bundle does not authenticate its signature or establish custody.


## 8. External anti-rollback witness checkpoint contract

The proposed machine-readable checkpoint is `docs/schemas/m0-ledger-anti-rollback-checkpoint.schema.json`. It binds an independently administered witness identity, environment and authority, monotonic checkpoint generation, exact authorization-ledger event sequence/digests, trust-bundle generation/digest, revocation generation/digest, and per-enrollment host epoch high-water marks. The checkpoint also carries a freshness nonce and signature/evidence references.

Before reopening authorization operations after restore or failover, the restored ledger must match the latest independently obtained witness checkpoint exactly for every anchored generation, sequence, digest and host high-water mark. A stale generation, missing checkpoint, unavailable witness, signature/freshness uncertainty, or any digest mismatch leaves the affected ledger read-only and authorizations QUARANTINED. There is no local-database fallback and no operator override that silently lowers the witnessed high-water mark.

The witness must be administered and stored outside the combined Neon, R2, guest and provider-account restore/failure domain. Its signing/custody authority, quorum, availability, anti-equivocation behavior, backup/restore and key-rotation procedure remain unselected and require independent review. The schema does not establish those properties.

## 9. Immutable evidence object receipt contract

The proposed receipt schema is `docs/schemas/m0-immutable-evidence-object-receipt.schema.json`. It records the exact object key and immutable version ID, content SHA-256 and size, provider/bucket reference, retention mode and deadline, legal-hold signal, object-lock configuration digest, writer identity, and a readback performed against that same version. The evidence acquirer and independent verifier are distinct from the writer and from each other.

Acceptance requires exact version-ID and digest equality after readback, a retention deadline covering the required period, an approved immutable retention mode, and principal separation. A provider value such as `compliance` or `legal_hold=true` is only recorded metadata until target-account API behavior and deletion/overwrite resistance are independently tested. The value `unverified` is never acceptable for authorization evidence.

Cloudflare R2 remains a candidate object store; this receipt schema does not assert that its versioning, object-lock, retention, legal-hold or immutable-version semantics satisfy the contract. No object-store credentials or signing keys are included.

## 10. Synthetic validation boundary

`scripts/validate_m0_witness_evidence_contract.py` validates both Draft 2020-12 schemas and exercises synthetic exact-checkpoint alignment, stale-anchor rejection, exact evidence-version readback, digest equality, retention horizon and principal-separation checks. It does not connect to Neon, an external witness or R2, and it does not verify signatures or provider retention behavior.


### Checkpoint succession and anti-equivocation continuity

Each checkpoint after the initial enrollment anchor must bind the exact prior checkpoint artifact digest in `previous_checkpoint_digest`; `checkpoint_sha256` identifies the exact serialized checkpoint artifact bytes, increment witness generation by exactly one, and preserve witness, authority and environment identity. Ledger event sequence, trust-bundle generation, revocation generation and each enrolled host's epoch high-water mark may never decrease; previously enrolled host identities may not disappear from the successor's high-water-mark set. A gap, fork, identity change or regression is a witness-integrity failure and quarantines authorization state. The synthetic validator exercises valid succession and rejects generation gaps, predecessor-digest mismatch, environment changes, trust/revocation rollback, ledger-sequence rollback and host-epoch rollback.

For evidence retention, only a compliance-mode or independently reviewed provider-immutable mode is eligible in the proposed acceptance predicate. Governance-mode retention is not accepted because privileged bypass behavior can undermine the intended immutable evidence guarantee. Provider semantics still require target-account tests; the validator only checks declared metadata.
